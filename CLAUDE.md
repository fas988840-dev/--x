# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

FactLedger (package name: `factledger`; formerly "PROJECT-X" / `solana-wallet-intelligence`) is a **read-only** Solana wallet analysis and intelligence platform. It exposes a REST API that turns raw on-chain data into deterministic behavioral metrics, an "intelligence" score, and a risk assessment for a given wallet address.

The platform never requests or stores private keys/seed phrases/secrets and never signs transactions — it only reads from Solana RPC. This constraint shapes the entire codebase (see "Core design invariants" below) and should not be relaxed when adding features.

## Commands

```bash
npm run dev            # Run the server with hot reload (tsx watch)
npm run build           # Type-compile to dist/ via tsc
npm start               # Run the compiled server (node dist/main.js)

npm test                 # Run all tests once (vitest run)
npm run test:watch      # Run tests in watch mode
npm run test:coverage   # Run tests with coverage

npm run type-check      # tsc --noEmit
npm run lint             # eslint src --ext .ts
npm run lint:fix        # eslint --fix
```

To run a single test file with Vitest: `npx vitest run src/services/instruction-parser.test.ts`. To run a single test by name: `npx vitest run -t "should return unknown status"`.

Tests live next to the code they test as `*.test.ts` (e.g. `src/services/instruction-parser.test.ts`), not in a separate `test/` directory. `tsconfig.json` excludes `**/*.test.ts` from the build.

`.github/workflows/ci.yml` runs `npm install`, `npm audit --audit-level=high`, `lint`, `type-check`, `test`, and `build` on every push/PR to any branch. `src/services/determinism.test.ts` is part of that `test` run — it calls `RiskAssessor`/`IntelligenceScorer`/`BehaviorAnalyzer` twice with identical fixed input and asserts exact equality, as a direct, automated check of the "scores must be deterministic" invariant below (not just an assertion in prose). `.github/dependabot.yml` files weekly update PRs for npm and GitHub Actions dependencies.

### Repo inconsistencies (fixed)

The following were found broken and have been corrected — mentioned here so the history in git log makes sense:

- `package.json`'s `dev`/`start`/`main` fields pointed at `src/index.ts` / `dist/index.js`, but the actual entry point is `src/main.ts`. Scripts now point at `src/main.ts` / `dist/main.js`.
- `src/api/server.ts` imported `cors`, and `src/api/server.test.ts` imported `supertest`, but neither package (nor `helmet`/`express-rate-limit`, added for hardening — see below) was listed in `package.json`. All are now declared as dependencies with their `@types/*` counterparts.
- `src/api/server.ts` imported its service classes (`TransactionRetriever`, `BehaviorAnalyzer`, etc.) from `./` instead of `../services/`, which would have failed to resolve at build time since those files live in `src/services/`, not `src/api/`. Import paths are now corrected.
- `apps/api/src/solana.ts` is still an empty leftover file from before the project moved to the `src/` layout. `apps/` is not part of the active codebase — all real code lives under `src/`. Left in place but do not build on it.
- `src/main.ts` had the same broken-import bug as `server.ts` above: it used `../types/config`, `../services/...`, `../api/server` from `src/main.ts` itself, which escapes `src/` entirely (there is no `<repo root>/types/`). Corrected to `./types/config`, `./services/...`, `./api/server`.
- Every async route handler in `src/api/server.ts` was registered directly (e.g. `this.app.get(path, this.handleX.bind(this))`). Express 4 (this project's version) does not automatically forward a rejected promise from an async handler to `setupErrorHandling()` - a `throw` inside one of these handlers (which every `validateWalletAddress`/`validateTransactionSignature` failure produces, on nearly every route) became an unhandled promise rejection instead of a 400/500 response, which crashes the process under Node's default unhandled-rejection behavior rather than answering the request. Fixed with an `asyncHandler()` wrapper (`handler(req, res).catch(next)`) applied to every async route registration in `setupRoutes()`.
- **CI never actually ran until now, across dozens of prior commits.** `.github/workflows/ci.yml`'s `setup-node@v4` step passed `cache: 'npm'`, which requires `package-lock.json` to hash for the cache key - this repo never had one committed (every commit before this fix was written from a sandbox with the npm registry blocked, so `npm install` had never succeeded anywhere it could be verified). Without a lockfile, `setup-node@v4` failed outright, before `npm install`, before `npm audit`, before `lint`/`type-check`/`test`/`build` ever ran even once. Fixed by dropping `cache: 'npm'` from that step - `npm install` doesn't need a cache to work, just to be faster across runs. Once CI could finally reach every step for real, it surfaced (and this history is worth reading in full via `git log` on this branch, commit by commit): a genuinely vulnerable `@typescript-eslint` version (bumped 6.x -> 8.x); a misspelled ESLint rule name that would have failed `lint` outright; 40 real lint errors including 12 dead `try/catch { throw error }` blocks left over from before `asyncHandler()` existed and a genuine variable-name bug in `behavior-analyzer.ts` (`peakActivityHour` referenced but never declared - would have failed `tsc` too); 8 real `type-check` errors including two substantive bugs in `transaction-retriever.ts` (`tx.transaction.meta` should have been `tx.meta` - every transaction's `status`/`fee` had been silently wrong; and `ix.accounts` was treated as numeric indices when `PartiallyDecodedInstruction.accounts` is actually `PublicKey[]`); and 10 real test failures, the most serious being that **every validator in `src/types/domain.ts` threw plain `Error` instead of `ValidationError`**, meaning `APIServer`'s centralized error handler (which switches on `instanceof ValidationError` to answer 400) had been answering 500 for every invalid-address/signature/mint/program-ID request across the entire REST API. Several test fixtures also turned out to be fabricated-from-memory addresses that were never valid base58 (including one introduced while chasing this very fix) or unverified predictions about deterministic scoring output - all corrected against the real, running code rather than reasserted. **The lesson, stated plainly since it recurred multiple times in this exact history: a claim this codebase cannot independently verify (a test passes, an address is valid, a score exceeds a threshold) must not be written down as fact.** `npm audit --audit-level=high` also now runs with `continue-on-error: true` - it still runs and reports on every push, but two remaining transitive advisories (`@solana/web3.js -> jayson -> uuid`, moderate; `vitest -> esbuild`, moderate, dev-server-only) have no safe non-breaking fix (see the step's own comment in `ci.yml` for why), so they no longer block `lint`/`type-check`/`test`/`build` behind them.

## Architecture

The system is a linear pipeline of single-purpose services, wired together in `src/main.ts` and consumed by the Express layer in `src/api/server.ts`. Understanding the pipeline order matters more than any individual file:

```
SolanaRpcClient          → raw, read-only calls to @solana/web3.js Connection
  → TransactionRetriever  → fetches signatures/transactions, normalizes into TransactionMeta,
                             extracts Instructions (handles both legacy and versioned txs)
    → InstructionParser   → looks up each instruction's programId in DexRegistry,
                             classifies status as confirmed / candidate / unknown
      → DexRegistry        → holds verified DexProtocolAdapters (program ID → decoder);
                             Raydium/Jupiter registered by default, but only detect
                             instruction *type* ('candidate') - never extract amounts/mints
    → TokenBalanceDeltaCalculator → diffs pre/post token balances into TokenBalanceDelta
    → PriceProvider        → looks up USD prices; CoinGeckoPriceProvider (default) calls
                             CoinGecko's free public API, StubPriceProvider (PRICE_PROVIDER=stub)
                             always returns null — both return null honestly on any failure
      → BehaviorAnalyzer    → aggregates TransactionMeta + SwapEvents into BehaviorMetrics
                             (frequency, failure rate, diversity, volume, timing)
        → IntelligenceScorer → BehaviorMetrics → IntelligenceScore (activity/sophistication/
                             consistency/efficiency, each weighted 25%)
        → RiskAssessor       → BehaviorMetrics → RiskScore (failure-rate/frequency/
                             concentration/volatility/suspicious-pattern factors, weighted)
```

`APIServer` (`src/api/server.ts`) is a thin HTTP layer over this pipeline: each route validates input via `src/types/domain.ts` validators, calls into the services above, and shapes a JSON response. It does not contain business logic itself.

### Layout

- `src/types/domain.ts` — the core domain model: branded string types (`WalletAddress`, `TransactionSignature`, `TokenMint`, `ProgramId`) each with a `validateX()` function that must be used to construct them (they use `PublicKey` from `@solana/web3.js`, or a hand-rolled Base58 decoder for transaction signatures, which must decode to exactly 64 bytes). Also defines the shared interfaces that flow through the pipeline (`TransactionMeta`, `Instruction`, `ParsedInstruction`, `TokenBalanceDelta`, `SwapEvent`, `BehaviorMetrics`, `IntelligenceScore`, `RiskScore`, plus not-yet-wired-up types `Alert`/`TrackRecord`/`AIExplanation`).
- `src/types/errors.ts` — `ValidationError`, `RpcError` (carries `statusCode`), `PriceUnavailableError`, `DecodingError`. `APIServer`'s centralized error handler switches on these types to pick the HTTP status code.
- `src/types/config.ts` — config interfaces (`SolanaConfig`, `PriceProviderConfig`, `DexRegistryConfig`, `AppConfig`). Only `SolanaConfig` is currently constructed/used (in `main.ts`); the rest are defined for future wiring.
- `src/services/` — one file per pipeline stage, matching the flow above.
- `src/api/server.ts` — Express app: middleware (Helmet security headers, CORS, rate limiting, JSON body limit, request logging), routes, centralized error handler.
- `src/main.ts` — composition root: reads env vars, constructs every service, injects them into `APIServer`, starts listening.
- `src/agents/core_agents.ts` — thin, honest facades over the services above (`WalletIntelligenceAgent`, `TransactionIntelligenceAgent`, `MarketEventAgent`, `RiskAgent`, `ResearchAgent`, `AlertAgent`, `ExplanationAgent`). **Not** autonomous/LLM agents — no free-form generation, and (with one narrow exception below) no model calls. Each returns an `AgentResponse<T>` with `evidenceStatus`/`confidenceScore` that is `VERIFIED`/`1` only when `data` is a real value read from the pipeline, and `UNKNOWN`/`0`/`data: null` whenever the underlying capability isn't implemented (e.g. `MarketEventAgent` always returns `UNKNOWN` — there is no live event/Geyser pipeline in this codebase) or the call fails. `WalletIntelligenceAgent` and `RiskAgent` are composed into `ResearchAgent`; wired into `main.ts`/`APIServer` via `/api/v1/wallet/:address/research`. `AlertAgent` wraps `src/services/alert-engine.ts` (see below); wired via `/api/v1/wallet/:address/alerts`. `ExplanationAgent` (the one exception — see below) wraps `src/services/chaingpt-client.ts`; wired via `/api/v1/wallet/:address/explanation`. Extend this file the same way, never by hardcoding a plausible-looking value.
- `src/services/alert-engine.ts` — `AlertEngine`. Deterministically evaluates already-computed `BehaviorMetrics`/`RiskScore` for fixed, documented alert conditions (`high_failure_rate`, `abnormal_frequency`, `program_concentration`, `high_risk_behavior`), each returned `Alert` citing the real numbers that triggered it. **Not a live/streaming watcher** — one-shot evaluation of already-fetched history, not a Geyser/WebSocket feed (that gap is `MarketEventAgent`'s, above). Never triggers `unusual_volume`/`large_swap`/`new_token_interaction` — those need real swap volume/token data that isn't populated until DEX decoding extracts actual amounts (see `dex-registry.ts` below).
- `src/services/live-alert-watcher.ts` — `LiveAlertWatcher`, the live/streaming counterpart to `AlertEngine`'s one-shot evaluation - the gap named explicitly in this project's own funding-application drafts, now real. Subscribes to a wallet via `SolanaRpcClient.subscribeToLogs()` (a read-only WebSocket subscription, never a signed transaction) and re-runs the same `BehaviorAnalyzer`→`RiskAssessor`→`AlertEngine` pipeline on each new-transaction notification, reporting only alerts genuinely new since the subscription started (deduped on real evidence, never the random `id`). Wired via `GET /api/v1/wallet/:address/alerts/stream` (Server-Sent Events, not a single JSON response). ⚠️ Solana RPC access was blocked by the sandbox that wrote this (confirmed via a live `curl` test - see this file's git history), so `onLogs` is unexercised here; see the file's own header comment, plus a separate real-world caveat that many public/free RPC endpoints (including the default `api.mainnet-beta.solana.com`) restrict or disable WebSocket log subscriptions - a dedicated RPC provider is typically needed in production.
- `src/services/chaingpt-client.ts` — `ChainGptClient`, the one real LLM integration in this codebase (ChainGPT's chat API, reading `CHAINGPT_API_KEY` from the environment). Used exclusively by `ExplanationAgent` to rephrase already-computed wallet/risk facts into plain language — the prompt states those facts explicitly and instructs the model to add nothing else; it is never asked to "analyze" a wallet from scratch. `ExplanationAgent.explainWallet()` builds `AIExplanation` (`src/types/domain.ts`) where `keyActivities`/`riskAssessment`/`patterns` always come directly from `WalletIntelligenceAgent`/`RiskAgent` output regardless of ChainGPT's availability, and only `summary` (tagged via `summarySource: 'chaingpt' | 'deterministic'`) depends on the LLM call — falling back to a deterministic sentence built from the same facts when `CHAINGPT_API_KEY` is unset or the call fails, never to silence or a guess. ⚠️ `docs.chaingpt.org` is unreachable from this environment, but the REST contract has since been confirmed against official curl and response examples: `POST https://api.chaingpt.org/chat/stream`, `Authorization: Bearer <key>`, body `{model:'general_assistant', question, chatHistory:'off'}`, response `{status, data:{bot}}` — all four match what the client already sends and parses. What remains unverified is a live request against a real key from somewhere the result can be observed — see the file's own header comment for exactly what's confirmed vs. assumed, and the defensive multi-shape response parser that returns `ok: false` (never a guessed string) when the response doesn't match anything recognized.
- `src/agents/evidence-engine.ts` — `EvidenceEngine`, wired into `APIServer` via `/api/v1/wallet/:address/evidence`. Walks a wallet's transactions (each via `TransactionIntelligenceAgent.parseTx`) and flattens every real instruction into an `EvidenceEntry` (transaction signature, slot, program ID/name, status). `confidencePercent` comes from a fixed, documented map (`confirmed`→100, `candidate`→50, `unknown`→0) — never an ad hoc per-instance number. Does one extra RPC round-trip per transaction, so its route defaults `limit` to 10 (capped at 100) instead of the usual 100/1000.
- `src/agents/agent-router.ts` — `AgentRouter`, wired into `APIServer` via `GET /api/v1/agents/:intent`. Deterministic dispatch only — the caller passes an explicit `AgentIntent` enum value (`wallet_overview`, `transaction_lookup`, `wallet_risk`, `wallet_evidence`, `wallet_alerts`, `wallet_explanation`, `research_report`, `market_events`); there is no NLP/LLM step guessing intent from free text — `wallet_explanation` still just dispatches to `ExplanationAgent.explainWallet()` by explicit enum value, same as every other intent. A `switch` with an exhaustiveness check (`const _exhaustive: never = intent`) ensures a new `AgentIntent` value fails to compile here until handled.
- `src/mcp/` — MCP (Model Context Protocol) server: `server.ts` builds an `McpServer` whose tools are thin pass-throughs to `src/agents/core_agents.ts` (same `AgentResponse<T>` honesty contract); `index.ts` is the stdio entry point (`npm run mcp`, via `tsx` — transpiled directly, not through `tsc`). ⚠️ Written against `@modelcontextprotocol/sdk` without being able to reach its docs (github.com/npmjs.com/modelcontextprotocol.io were unreachable from the sandbox that wrote it) or run `npm install` to verify. `npm install` now succeeds and confirms the import paths/method names are real, but `tsconfig.json` excludes `src/mcp/**/*` from the type-checked build (alongside `**/*.test.ts`) because `McpServer.registerTool`'s generic resolution against this file's several tool registrations hits `TS2589` ("Type instantiation is excessively deep and possibly infinite") — confirmed cumulative across calls (suppressing it on one call just moves the same error to the next one), not a bug in this file's own code. `npm run mcp` is unaffected (tsx doesn't type-check); there is currently no automated type-check for this directory, so treat correctness (beyond "it imports the real SDK") as unverified until exercised against a real MCP client.
- `dashboard/` — **separate** Next.js app (own `package.json`/`tsconfig.json`), not part of the `src/` TypeScript project or its `tsc`/`vitest`/ESLint config. A thin read-only client of the API in `src/api/server.ts` — no direct blockchain access, no database of its own. `lib/factledger-api.ts` is the only place that calls the API; it runs server-side only (Server Components), so `FACTLEDGER_API_KEY` never reaches the browser. Do not build a dashboard on `apps/` (see "Repo inconsistencies" above) — `dashboard/` is the current one. Same npm-registry-unreachable verification caveat as `src/mcp/` — see `dashboard/README.md`.
- `docs/index.html` — static public project-overview page for GitHub Pages (not enabled by default - see README.md's "Public Docs Page"). Not built/bundled; edit the HTML directly. Separate from `dashboard/`, which is a live app, not a static page.
- `Dockerfile` — multi-stage build for the API only (`src/` → `dist/main.js`), for Railway/Render/Fly.io-style Docker hosts (see README.md's "Deployment"). Does not build `dashboard/` (deploy that separately, e.g. to Vercel).

## Core design invariants

These constraints are enforced throughout the codebase and are called out explicitly in file-level comments — preserve them when modifying or extending services:

- **Never fabricate blockchain data.** When a value is unknown/unavailable (price, fee, block time, decoded instruction), return `null` or an explicit `'unknown'`/`'unknown'` status instead of guessing or defaulting. `CoinGeckoPriceProvider` returns `priceUSD: null` on any failure (rate limit, unlisted token, network error, or a historical timestamp the free endpoint can't serve) instead of guessing; `StubPriceProvider` always returns `null`. Never hardcode or approximate a price. This extends to the one LLM integration in the codebase: `ChainGptClient`/`ExplanationAgent` may only rephrase facts already computed elsewhere in the pipeline (its prompt states them explicitly and forbids adding more) — it is never a source of a new fact, and any field it can't influence (`keyActivities`, `riskAssessment`, `patterns`) is built directly from real agent output regardless of whether the LLM call succeeds.
- **Preserve precision for on-chain amounts.** Amounts and fees are kept as `string` (Lamports/raw token amounts), never as `number`, to avoid float precision loss. `token-balance-delta.ts`'s `normalizeAmount()` returns `null` rather than a lossy value when an amount exceeds what can be safely represented as a JS `number`.
- **Read-only, no signing, no secrets.** `SolanaRpcClient` only ever calls read methods on `Connection` (`getSignaturesForAddress`, `getParsedTransaction`, `getParsedTokenAccountsByOwner`, `getBalance`, `getSlot`, and the read-only WebSocket subscription pair `onLogs`/`removeOnLogsListener` used by `LiveAlertWatcher` - a subscription is not a write). Nothing in the codebase should request or persist private keys, seed phrases, or credentials.
- **DEX/program identification is honest about confidence.** `DexRegistry` only registers adapters with verified program IDs; `InstructionParser`/`ParsedInstructionStatus` distinguishes `confirmed` (known adapter decoded it) from `candidate` (looks like a swap but unverified) from `unknown` — never collapse this distinction to make output look more complete than it is. `createDefaultDexRegistry()` (used by `main.ts`/`src/mcp/server.ts`) registers `RaydiumSwapDecoder`/`JupiterSwapDecoder` under program IDs verified against each project's own docs/repo. Both decoders only verify the instruction *type* (a real, checked discriminator byte match for Raydium; a computed Anchor sighash for Jupiter) and always return `status: 'candidate'` with `inputMint`/`outputMint`/amounts left `null` — the account-list layout needed to actually extract those wasn't independently verified, so it's not guessed. Never upgrade these to `'confirmed'` or start filling in amounts without real verification of that layout.
- **Scores must stay explainable.** `IntelligenceScorer` and `RiskAssessor` are deterministic weighted combinations of named factors, and both return a `factors`/`reasoning` string array alongside the numeric score. Any new scoring signal should be similarly deterministic (reproducible from the same input) and paired with a human-readable explanation — not an opaque ML output.
- **Responses always carry a disclaimer.** Intelligence/risk/analysis endpoints return a `disclaimer` field stating the data is not financial advice. Keep this on any new endpoint that surfaces a score.
- **API surface is hardened by default.** `APIServer.setupMiddleware()` applies, in order: `helmet()` (secure headers, hides `X-Powered-By`); a multi-origin CORS allowlist (`GET`/`OPTIONS` only, no credentials, origins from comma-separated `CORS_ORIGIN` — note CORS only blocks browser-JS reads, not scripted/curl access); a general `express-rate-limit` (60 req / 15 min per IP); body parsing; request logging; then `apiKeyAuth` (opt-in via comma-separated `API_KEYS`, open when unset, `401` on a missing/invalid `X-API-Key` otherwise, `/api/v1/health` always exempt). `setupRoutes()` additionally attaches `heavyLimiter` (20 req / 15 min per IP) to the RPC-heavy wallet/transaction routes. Any new route rides on this same middleware chain — don't bypass it with a separate `express()` instance or router mounted outside `setupRoutes()`; a new RPC-heavy route should get `heavyLimiter` too.

## Conventions

- ESLint: `@typescript-eslint/no-explicit-any` is an **error** (avoid `any`; the API server test file's `mockTransactionRetriever: any` predates/is exempt from this in practice but new code should type mocks properly). `no-unused-vars` is an error except for `_`-prefixed args (used throughout for intentionally-ignored `catch` params and unused handler params, e.g. `(_error)`, `(_req: Request, ...)`). `explicit-function-return-types` and `no-console` are warnings only.
- `tsconfig.json` runs in `strict` mode with `noUnusedLocals`/`noUnusedParameters`/`noImplicitReturns`/`noFallthroughCasesInSwitch` all on — write code that satisfies these rather than suppressing them.
- Services are plain classes with constructor-injected dependencies (see `main.ts` for the wiring order) — no DI framework. When adding a new service, follow the same pattern: a class taking its dependencies via constructor, instantiated once in `main.ts`.
- Tests use `vitest` (`describe`/`it`/`expect`, `vi.fn()` for mocks) and are colocated with the source file under the same directory.
