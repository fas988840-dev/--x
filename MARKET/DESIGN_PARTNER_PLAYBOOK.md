# FactLedger — Design Partner Playbook

## Objective

Recruit 5–10 qualified design partners before broad feature expansion. The purpose is to learn which evidence, risk, API and agent workflows create repeated value and willingness to pay.

## Priority segments

1. Solana wallets and explorers
2. compliance / investigation / forensics teams
3. trading, treasury and risk platforms
4. protocols that need wallet/transaction context
5. AI/agent builders consuming structured blockchain intelligence

## Qualification criteria

Prefer teams that:
- already process Solana wallets or transactions
- have a recurring risk/evidence workflow
- can integrate an API or agent tool
- can provide concrete feedback within 1–2 weeks
- have a plausible path to paid usage

Avoid counting casual interest, social followers or one-off demos as a design partner.

## Outreach message template

Subject: Explainable Solana wallet/transaction risk — design partner

FactLedger is building an evidence and risk intelligence layer for Solana. Instead of returning only a black-box score, the API is designed to return attributable evidence, risk context, explanations and machine-readable outputs for apps and agents.

We are selecting a small set of design partners to test the production workflow and shape the next integrations. The ask is simple: try one real workflow, tell us what is missing, and help us validate whether this should become part of your stack.

No partnership, customer or integration should be publicly claimed unless both sides have actually agreed to it.

## Discovery questions

- What Solana wallet/transaction decision are you trying to make?
- What data do you currently collect manually?
- Which false positive/false negative is most costly?
- Do you need a score, evidence, provenance, explanation, alerts, history, or all of these?
- What response latency is acceptable?
- Would this be called synchronously, in batch, or through an agent?
- What would make you pay for it?
- What security/compliance requirements block adoption?

## Pilot definition

A pilot must have:
- named use case
- integration owner
- success metric
- test window
- feedback checkpoint
- decision date

Suggested success metrics:
- reduction in manual investigation time
- evidence coverage
- successful analyses
- API latency/error rate
- repeat usage
- decision usefulness

## Weekly operating metrics

Track only source-of-truth values:
- qualified organizations contacted
- replies
- discovery calls
- active pilots
- external integrations
- repeated API users
- conversion to paid
- top three recurring requests

## Feature-priority rule

Prioritize an integration when it has one or more of:
1. repeated request from qualified users
2. measurable improvement in evidence quality
3. direct revenue path
4. strategic distribution value

Otherwise defer it.
