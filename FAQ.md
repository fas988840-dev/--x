## 🧠 About the Project

### Q1: What problem does FactLedger solve?

Wallet analysis tools on Solana currently split into two unsatisfying categories:

1. **Heuristic tools** that pattern-match program IDs loosely, mislabeling unverified programs as swaps
2. **Commercial analytics** that return opaque scores users cannot audit

FactLedger addresses this gap by enforcing honesty in code: every value is either independently verified or explicitly null, and confidence is tiered (confirmed/candidate/unknown) rather than collapsed into one apparent answer.

### Q2: How is this different from existing tools?

Three key differences:

1. **Determinism enforced by CI** — Not a documentation promise. Every score is generated by pure functions verified by automated tests on every push.

2. **Explicit "unknown" over guesses** — When we can't verify something (price, decoded amount, protocol), we return null. Other tools substitute plausible-looking estimates.

3. **Reviewable evidence** — Every score cites the specific transactions and program IDs that produced it. Any reviewer can pull those from a public RPC and reproduce the calculation.

### Q3: Why did you build it as read-only?

Three reasons:
- **Security**: No private keys means no attack surface for fund theft
- **Trust**: Users don't need to give any secrets to use it
- **Composability**: Read-only APIs are safer to build applications on top of

### Q4: What's the current maturity level?

- 133 tests passing (verified by GitHub's CI runners)
- Full TypeScript strict mode with no `any` types
- Determinism check runs automatically on every push
- Production-ready Docker build
- Honest about limitations: swap amounts not yet extracted, live WebSocket unexercised against real RPC

## 🔧 Technical Questions

### Q9: What's the tech stack?

- **Runtime**: Node.js 18+ with TypeScript
- **Blockchain**: `@solana/web3.js` (read-only)
- **API**: Express.js with Helmet, CORS, rate limiting
- **Testing**: Vitest (133 tests)
- **Deployment**: Docker (multi-stage build)
- **CI/CD**: GitHub Actions

### Q10: Why TypeScript strict mode?

Strict mode catches whole classes of bugs at compile time:
- No implicit `any` types
- No implicit returns
- No unused variables
- No fallthrough in switch statements

This aligns with the project's honesty principle — the compiler enforces what would otherwise be documentation promises.

### Q11: How do you handle blockchain data precision?

All amounts and fees are kept as **strings** (representing lamports or raw token units), never JavaScript numbers. `normalizeAmount()` in `token-balance-delta.ts` returns `null` rather than a lossy value when amounts exceed safe integer range.

This is critical: converting a large lamport amount to a JS number silently loses precision. We refuse to do that.

### Q12: How is "determinism" enforced?

`src/services/determinism.test.ts` calls each scoring function twice with identical input and asserts exact equality. This runs on every push via CI. If any code change makes the scoring nondeterministic, the build fails.

### Q13: What DEXs do you support?

Currently: Raydium AMM V4 and Jupiter V6 — detected as **candidate** status (instruction type verified, but account layout not verified for amount extraction).

Planned (with grant funding): Orca, Magic Eden, Phantom Swap. Each will be verified against official sources before promotion to **confirmed** status.

### Q14: Do you use LLMs / AI?

Yes, but very narrowly. `ChainGPT` is used only as an "explanation layer" — rephrasing already-computed, deterministic facts into plain language. The LLM never originates facts. Its prompt states the facts explicitly and instructs it to add nothing else. If ChainGPT is unavailable, we fall back to a deterministic summary sentence built from the same facts.

The critical fields (`keyActivities`, `riskAssessment`, `patterns`) are ALWAYS built from real agent output, never from the LLM.

## 🤔 Skeptical Questions

### Q19: Isn't this just a wrapper around Solana RPC?

No. FactLedger adds several layers of value:

1. **Verified DEX detection** — Not just program ID lookup; verified against instruction discriminators
2. **Deterministic scoring** — Reproducible metrics from raw transaction history
3. **Confidence tiering** — Explicit honesty about what we know vs. don't know
4. **Precision-preserving amounts** — String-based arithmetic that RPC doesn't provide
5. **Aggregated behavior** — Frequency, diversity, timing patterns computed correctly

### Q20: Why should users trust your scoring model?

Because they don't have to. Every score:
- Comes with `factors` (the computed inputs)
- Comes with `reasoning` (human-readable explanation)
- Is verifiable — reviewers can pull our cited transactions from any RPC and recompute

Trust isn't the mechanism; **verification is**.

### Q21: What if a bigger team builds this?

Then Solana wins. The mission is honest wallet intelligence in the ecosystem. If someone else builds better versions of these ideas, I'll cheer them on. The code is MIT-licensed for a reason.

That said, I've deliberately made design choices (honest confidence tiering, refusing to guess) that many commercial teams would find business-hostile. Being open and honest is my competitive advantage.

### Q22: Have you talked to potential users?

Not extensively yet — that's part of what the grant funds. Milestone 3 is specifically about ecosystem integration and community engagement.

### Q23: Isn't the license too permissive (MIT)?

MIT lets anyone build on this. That's a feature, not a bug. The goal is ecosystem improvement, not extracting rent. If someone builds a commercial product on top, they still improve the underlying open code (which I maintain).

## 📊 Operational Questions

### Q24: How will you handle uptime?

Milestone 1 includes monitoring (Sentry for errors, UptimeRobot or similar for availability). Target: 99.5% uptime for the free tier.

### Q25: What about rate limiting and abuse?

The Express server has `express-rate-limit` configured:
- General: 60 req / 15 min per IP
- RPC-heavy routes: 20 req / 15 min per IP

Optional API key authentication via `API_KEYS` env var for production use.

### Q26: How do you handle RPC costs?

Public endpoints (mainnet-beta.solana.com) are free but rate-limited. Milestone 1 funds moving to a dedicated provider (Helius free tier or paid tier).

### Q27: What about GDPR/privacy?

FactLedger reads only public blockchain data. No personally identifiable information is collected, stored, or transmitted. The API doesn't require user accounts or store queries.

### Q28: Sustainability beyond the grant?

Milestone 3 explicitly funds establishing a sustainability model. Options include:
- API credit tiers for high-volume users
- Sponsored protocol integrations
- Enterprise support contracts
- Community donations / Gitcoin
