📌 بيان المشكلة (Problem Statement)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Wallet analysis on Solana today splits into two unsatisfying categories.

Heuristic tools claim to detect DEX activity by pattern-matching program IDs loosely. Raydium and Jupiter each ship multiple program versions; unverified programs are routinely mislabelled as swaps. Users act on this data believing it was verified.

Commercial analytics return risk and reputation scores from proprietary models. A user cannot audit the score, cannot reproduce it, and cannot tell which transactions drove it. When such a score gates access to a protocol or informs a counterparty decision, that opacity is a real cost.

Neither category tells the user what it does not know. That is the gap FactLedger addresses.

📌 الحل والابتكار (Solution & Innovation)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FactLedger is a read-only Solana wallet intelligence API built on two design rules enforced in code rather than promised in documentation:

1. It never fabricates. Any value the platform cannot verify — a price, a fee, a decoded swap amount — is returned as null or an explicit 'unknown', never as a plausible-looking estimate.

2. It never overstates confidence. Every DEX instruction is classified 'confirmed', 'candidate', or 'unknown' against independently verified program IDs. These three states are never collapsed into one to make output look more complete.

Key innovations:
- Deterministic scoring (verified in CI on every push)
- Transparent factors and reasoning for every score
- String-based amount preservation (no float precision loss)
- Read-only construction (no signing, no key material)
- 12 REST endpoints + MCP server + Next.js dashboard
- Docker-ready for one-click deployment

📌 لماذا يهم هذا لسولانا (Why It Matters for Solana)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Wallet reputation and risk data increasingly gate real decisions — protocol access, counterparty trust, compliance workflows. When that data is a black box, mistakes are invisible and uncorrectable.

FactLedger offers the ecosystem a reference implementation for the opposite approach:
- Scores that cite their evidence
- Confidence that is tiered honestly
- Gaps that are stated rather than filled with guesses

It is open source, so any team can audit the method or build on it. This makes it valuable for:
- Developers: Build apps on verifiable wallet data
- Researchers: Audit and extend the system
- Compliance teams: Transparent metrics for AML/KYC
- Users: Honest analysis without black-box models

📌 القيود الصادقة (Honest Limitations)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Stating these is consistent with how the software itself behaves:

1. Swap amounts are not extracted. Raydium and Jupiter detection verifies the instruction type but not the account-list layout needed to read input/output mints and amounts. Those fields stay null and status stays 'candidate'.

2. Live WebSocket alert stream is unexercised against real endpoint. It is unit-tested against a mocked RPC client only. Public RPC endpoints often restrict log subscriptions.

3. No live deployment yet. Docker image builds; not deployed to public URL. That is Milestone 1.

4. No users yet. There are no usage numbers, and this proposal claims none.

📌 لماذا أنا (Why You / Why Me)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

I built this because the existing wallet analytics landscape on Solana forced a choice between opaque commercial tools and heuristic guessing that mislabels its outputs as facts. Neither is honest with users.

My approach was to enforce honesty in code rather than in documentation. Determinism is verified automatically in CI. Confidence tiers cannot be collapsed. Prices that fail return null, not a plausible number. Every score cites its evidence. If a reviewer wants to check any output, they can pull the transactions we cite from any public RPC and recompute by hand.

I work full-time on this as a solo developer. The codebase is 133-tests-passing on GitHub's own runners, not sandbox promises. Everything I claim can be independently verified from the CI badge or by cloning the repo and running `npm test`.
